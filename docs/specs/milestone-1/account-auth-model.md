# Spec: Account/Auth Model

## Purpose

Provide the authentication system for Milestone 1 login and auth token issuance.

## Two-Phase Auth Model

Authentication and game session creation are separated:

1. `LOGIN` → validates credentials → returns `authToken` (valid 300s, rolling)
2. `PLAY` → consumes `authToken` → creates `accounts_sessions` record → returns `sessionId`

The `authToken` is an in-memory UUID held by the server; it is not persisted to the database. It expires 300 seconds after last use, with each authenticated request resetting the expiry.

## Functional Requirements

- Look up account by username.
- Verify password using **Argon2id** against the stored PHC hash.
- Validate account status (`active`) before issuing an auth token.
- Return explicit result codes on all paths.
- Prevent game session creation unless an auth token is held.

## Result Codes (Implemented)

| Code | Condition |
|---|---|
| `OK` | Login successful, authToken issued |
| `INVALID_CREDENTIALS` | Username not found or password wrong |
| `ACCOUNT_DISABLED` | Account status is not `active` |
| `SERVER_ERROR` | Database or backend failure |

Note: failure paths return `LOGIN_ERR` message type with the code; success returns `LOGIN_OK`.

## Data Contract

```
accounts table:
  id            BIGSERIAL PRIMARY KEY
  username      VARCHAR(64) NOT NULL UNIQUE
  password_hash TEXT NOT NULL              -- Argon2id PHC format
  status        VARCHAR(16) DEFAULT 'active'
  created_at    TIMESTAMPTZ
```

## Password Hashing Standard

- **Algorithm:** Argon2id
- **Format:** PHC string (`$argon2id$v=...`)
- **Parameters:** iterations=3, memory=65536 KiB, parallelism=1 (configurable via constants)
- **Salt:** unique per password, generated by the Argon2 library
- **Library:** `de.mkammerer:argon2-jvm`

## Auth Token Lifecycle

- Issued as a random UUID on successful `LOGIN`
- Stored in `ConcurrentHashMap<String, AuthTicket>` on the server (in-memory)
- Expiry: 300s from last authenticated request (rolling)
- Consumed/invalidated: implicitly when the ticket window expires; explicitly cleared on `PLAY` (session creation)
- A scheduled task cleans expired tickets every 10 seconds

## Non-Functional Requirements

- Password verification timing is constant (handled by argon2-jvm `verify`)
- Failure path does not distinguish "username not found" from "wrong password" in the response
- Auth events are logged with user/account ID and reason at INFO level

## Milestone 1 Done Criteria

- [x] Server validates credentials and returns `LOGIN_OK` with `authToken`
- [x] Only requests carrying a valid `authToken` can proceed to character/play operations
- [x] Auth tokens expire and are cleaned up by the scheduler
